# Архитектура

## Защо „остров“, а не SPA

Проектът е Django с server-side темплейти и няма React. Пълен SPA би значел
пренаписване на навигацията, футъра, SEO-то и рутирането — работа, която тази
задача не изисква и не оправдава.

Затова: Django рендерира страницата и празен `<div id="apply-root">`, а React
се монтира само в него. Всичко останало остава както е.

```
Браузър
  │
  ├── GET /zapisvane-za-brigada/ ──→ Django (pages.zapisvane)
  │      └── HTML + data-bootstrap {season, turnstileSiteKey, offices}
  │      └── <script> от manifest.json през django-vite
  │
  └── React се монтира в #apply-root
         │
         ├── GET  /api/v1/lookup/{kind}?q=…   (debounce 250 ms)
         ├── PUT  /api/v1/applications/draft  (debounce 1200 ms)
         └── POST /api/v1/applications
                  │
                  ├─ 1. Turnstile проверка          ← преди да пипнем брояча
                  ├─ 2. Валидация (serializers)
                  ├─ 3. Транзакция: резервирай номер + запиши заявката
                  ├─ 4. docxtpl → LibreOffice → PDF  ← извън транзакцията
                  └─ 5. Celery: имейл с 3 прикачени файла
```

## Защо този ред на стъпките

**Turnstile е първи**, защото всяка следваща стъпка има цена: номер от
поредицата, дисково място, имейл от нашия домейн.

**Номерът се резервира в транзакция с записа**, за да няма два договора с
един номер при едновременни подавания (`SELECT … FOR UPDATE` върху брояча).

**PDF-ът се генерира извън транзакцията**, защото LibreOffice отнема секунди
и не бива да държи ред заключен толкова дълго.

**Имейлът е последен и е в опашка.** Той е най-крехката стъпка — SMTP може да
е бавен или недостъпен. Договорът вече е издаден; не бива да губим това заради
имейл. `transaction.on_commit` гарантира, че Celery няма да види некомитнат ред.

## Разделяне на отговорностите в бекенда

| Файл | Отговорност | Не знае за |
| --- | --- | --- |
| `validators.py` | бизнес правила като чисти функции | Django, DRF, HTTP |
| `serializers.py` | форма на входа, съобщения за грешки | база, файлове |
| `services.py` | оркестрация, транзакции | HTTP, заявки |
| `views.py` | HTTP: статуси, хедъри, throttling | как се прави договор |
| `contracts.py` | docx → PDF | защо и за кого |
| `emails.py` | какво пише в имейла | кога се праща |
| `tasks.py` | опити, изчакване, отказ | съдържание |

`validators.py` е без зависимости нарочно: същите правила се използват в
сериализаторите, в бъдещ админ импорт и в тестовете, които вървят за
милисекунди без база.

## Frontend

| Файл | Отговорност |
| --- | --- |
| `applySchema.ts` | zod схема — огледална на `serializers.py` |
| `payload.ts` | camelCase ↔ snake_case, изрично |
| `api.ts` | CSRF, форма на грешките, идемпотентност |
| `hooks.ts` | debounce, отмяна на изпреварени заявки, кеш |
| `ApplyWizard.tsx` | стъпки, степер, навигация, submit |

Валидацията е дублирана нарочно: zod дава мигновена обратна връзка,
Pydantic/DRF пази истината. **При промяна се пипат и двете.**

## Дублирането, което приемаме съзнателно

Три места знаят бизнес правилата: `validators.py`, `applySchema.ts` и
тестовете. Алтернативата — генериране на TypeScript от OpenAPI схемата —
добавя build стъпка и зависимост заради ~15 правила, които се менят веднъж
годишно. Ако правилата станат значително повече, преоцени решението.
